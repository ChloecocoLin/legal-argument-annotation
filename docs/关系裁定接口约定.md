## 1. 一句话说清这条链在干什么

命题裁定冻结出**统一命题集合** → 关系端点先映射到统一命题集合（**防悬空端点**）→ 两两比较各源版本的关系，产出**裁定项**（差异项 + 一致项）→ 裁定者逐项决定 → 合并出**正式论证图**。

硬顺序：**命题不冻结，不许开关系裁定**。未冻结时 J06 返回 `PROPOSITIONS_NOT_COMPLETE`（HTTP 409）。

## 3. J06（契约接口，已实现）

```
GET /api/v1/adjudication-sessions/{sessionId}/relation-items
```

| 参数 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `sessionId` | path | 是 | 裁定会话 ID（uuid） |
| `status` | query | 否 | `OPEN` / `DECIDED` / `ESCALATED` / `RETURNED` |
| `conflictType` | query | 否 | `EXISTENCE` / `TYPE` / `DIRECTION` / `PARTICIPANTS` / `AGREEMENT` |
| `page` | query | 否 | 默认 1 |
| `size` | query | 否 | 默认 20，最大 100 |

响应（信封 `success/data/meta/error`，`meta = {page, size, total}`）：

```jsonc
{ "success": true,
  "data": { "items": [ /* 见下 */ ] },
  "meta": { "page": 1, "size": 20, "total": 8 } }
```

**item 的字段（★ = 契约声明之外的追加字段，见 §9 偏差 g）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` ★ | string | 裁定项 ID |
| `conflictType` | string | 五值之一，见 §5 |
| `dimension` ★ | string | 冲突维度的中文标签，比 conflictType 细一档：`参与命题` / `组合成员` / `嵌套层级` / `方向` / `关系类型` / `一方新增` / `一方遗漏` / `一致项` |
| `reason` ★ | string | **中文差异理由，可直接显示给裁定者**。例：`方向相反：V1 为 S(P2,P3)，V2 为 S(P3,P2)；有向关系的 SOURCE 与 TARGET 必须二选一。` |
| `candidateRelationIds` | string[] | 两侧候选；**可为空数组表示"缺失一侧"**（存在性差异） |
| `candidates` ★ | object[] | 与 `candidateRelationIds` 同序的可读候选，见下 |
| `status` | string | 初始一律 `OPEN` |
| `decisionId` | string \| null | 决定 ID。**写侧归 D**，当前恒为 `null` |
| `nestedFirst` ★ | boolean | 该项任一候选含关系型端点（嵌套关系）。界面应提示**先裁内层** |

`candidates[]`：

```jsonc
{ "relationId": "v1-s2", "versionId": "av-1", "versionLabel": "V1",
  "relationCode": "S", "expression": "S(P2,P3)", "unmapped": false,
  "participants": [ { "id": "…", "ordinal": 1, "role": "SOURCE",
                      "targetKind": "ELEMENT", "targetId": "v1-p2",
                      "displayNo": "P2", "labelCode": "GM-L", "text": "…" } ] }
```

- `versionLabel` 是 **V1/V2**，直接当"采用A版/采用B版"的按钮文案。
- `expression` 是显示用公式（如 `S(J(P2,P3),P5)`），**后端不存**，读时生成。
- `unmapped: true` 表示该候选的某个端点映射不到统一命题集合 → 界面必须提示「请先完成该命题的裁定」，不能让裁定者对着不可比的候选做决定。

**错误**：`PROPOSITIONS_NOT_COMPLETE`(409) 命题未冻结；`NOT_FOUND`(404) 会话不存在；`INSUFFICIENT_VERSIONS`(400) 源版本少于两个。

## 4. 生成关系裁定结果（**非契约接口**，C 的试算/交付物）

契约把裁定**写入**归 D（J07/J08），所以本接口不是契约接口：它**只读试算、不落库**，是 `分工.md` §四.8 的交付物本身（关系裁定结果 + 正式论证图）。D 的 J07/J08 就绪后，把"决定"的来源从请求体换成已落库的 `AdjudicationDecision` 即可，语义算法不变。

```
POST /api/v1/adjudication-sessions/{sessionId}/relation-result
```

请求：

```jsonc
{ "unifiedSnapshotId": "us-1",           // 可省略，默认取会话的
  "decisions": [
    { "itemId": "…", "action": "ADOPT_VERSION",
      "sourceVersionId": "av-2",          // 二选一：按版本采用
      "sourceObjectId": "v2-s2",          // 二选一：精确指定候选关系
      "reason": "P3 才是被支持项" },
    { "itemId": "…", "action": "CUSTOM",
      "customRelation": { "relationCode": "S", "participants": [
        { "ordinal": 1, "role": "SOURCE", "targetKind": "ELEMENT", "targetId": "us-p6" },
        { "ordinal": 2, "role": "TARGET", "targetKind": "ELEMENT", "targetId": "us-p8" } ] } }
  ] }
```

响应 `data`：

| 字段 | 说明 |
|---|---|
| `status` | `COMPLETE` / `INCOMPLETE` / `INVALID`，判定优先级见 §6 |
| `conflictCount` / `agreementCount` | 分歧项数 / 一致项数（用于双进度条：`已裁/分歧`） |
| `decidedCount` | 本次计入"已裁"的项数 |
| `pendingItemIds` | 未给决定，或决定是 `RETURN` / `ESCALATE_EXPERT` |
| `reAdjudicationItemIds` | **决定不成立、必须重新裁定**的项（见 §6.3） |
| `relations[]` | 合并后的关系，`ownerType=FINAL_VERSION`、`ownerId=统一命题集合`，`sourceRelationIds` 记录被采用来源（自定义关系为空） |
| `issues[]` | `{code, level, message}`，`level` = `ERROR` / `WARNING` |
| `graph` | 正式论证图，形状同 GR01 的 `GraphView`：`nodes[] / edges[] / componentCount / isolatedNodeIds[] / graphId="session:<会话>"` |

**状态判定优先级（照此实现，勿自行更改）**：

1. 有任何 `ERROR` 级 issue → `INVALID`
2. 否则 `pendingItemIds` 或 `reAdjudicationItemIds` 非空 → `INCOMPLETE`
3. 否则 → `COMPLETE`

## 5. 枚举

**conflictType（契约声明，五值）**

| 值 | 含义 | 界面文案 |
|---|---|---|
| `EXISTENCE` | 一方建了、另一方没建 | 仅 A 版新增 / 仅 B 版遗漏 |
| `TYPE` | 端点相同、关系类型不同 | 关系类型分歧 |
| `DIRECTION` | 同类型、SOURCE 与 TARGET 互换 | 方向分歧 |
| `PARTICIPANTS` | 同类型、参与项不同（含叶命题、组合成员、嵌套层级三种细分，看 `dimension`） | 参与项分歧 |
| `AGREEMENT` | 两版一致 | 一致 |

**裁定动作（六个，归 D 的对象字典）**：`ADOPT_VERSION`（采用某版本）/ `CUSTOM`（自定义关系）/ `DELETE`（删除该关系）/ `RETURN`（退回）/ `ESCALATE_EXPERT`（提交专家）/ `CONFIRM_AGREEMENT`（确认一致）。

- `RETURN`（退回重标）与 `ESCALATE_EXPERT`（提交专家）**不消费裁定项**，项留在待办里。
- 每次操作**追加**一条决定，不覆盖旧决定；`/relation-result` 取该项的**最后一条**。
- `CUSTOM` 必须带 `customRelation`，否则 400。
- `ADOPT_VERSION` 若同时给了 `sourceObjectId` 与 `sourceVersionId`，以 `sourceObjectId` 为准。

## 6. 裁定语义规则（C 的核心算法）

### 6.1 端点先映射
所有端点先映射到统一命题集合再比较/合并。映射不到的端点不会产出悬空边，而是让该决定不成立并进 `reAdjudicationItemIds`，同时报 `INVALID_RELATION_MAPPING`。

**有一条被实测逼出来的细则：只要一侧含映射不上的端点，这条关系就完全不参与打分配对**（`pairScore` 直接返回 0），统一落为存在性差异并在理由里提示人工核查。

> 为什么必须这样：未映射的端点不会进 `leaves`，**分母凭空变小、重合度虚高**。实测 `S(P1,P2)` 对一条端点为「映射不上」的关系会算出 `1/2 = 0.5`，恰好越过阈值被判成"参与命题分歧"——而真相是"这条关系还不具备可比性"。可比才比，不可比就别比。

### 6.2 嵌套先裁内层
裁定项按候选的**最大嵌套深度升序**处理；外层的 `RELATION` 端点解析到内层**已合并**的关系。**嵌套不压平**——`S(J(P2,P3),P5)` 合并后仍是原结构。

### 6.3 引用已删除对象的决定不成立
先删了内层 `J(P2,P3)`，再采用引用它的外层 `S(J(P2,P3),P5)` → 外层决定**不算数**，进 `reAdjudicationItemIds`，并报 `NESTED_REFERENCE_EXISTS`(ERROR)，会话不能进入最终审查。这是"删除不级联、由裁定者显式处理"的落地。

### 6.4 明示的候选必须存在
`sourceObjectId` 给出却不在该项候选内 → **400，不静默改采第一条**。`sourceVersionId` 指定了但该项没有来自该版本的候选 → 同样 400。

### 6.5 自定义关系走同一套校验
`CUSTOM` 与 R02 用**同一个** `RelationValidator`（含 §1.1 参与矩阵、非命题不能参与、同快照等）；校验不过 → 该决定不成立，项进 `reAdjudicationItemIds`。

### 6.6 差异比较的配对优先级
逐条基准关系对所有候选**打分取最优**（不是按类型依次贪心）：

| 分 | 条件 |
|---|---|
| 4 一致 | 结构键相同（无向关系另用角色键） |
| 3 方向 | 有向、代码相同、端点集合相同而角色互换 |
| 2 参与项 | 同代码且**叶命题 Jaccard 重合度 ≥ 0.5** |
| 1 类型 | 代码不同但端点集合相同 |
| 0 | 不配对 → 各成一条 `EXISTENCE` |

同分再比重合度，仍同分按关系 ID 稳定排序。

> **为什么必须打分而不是贪心**：种子 `ses-1` 上贪心实现会把 `J(P2,P3)` 先判成与 `S(P3,P2)` 的 TYPE，抢走它本该配对的 `J(P2,P3,P4)`（PARTICIPANTS），并连带让 `S(P2,P3)` 失去配对退化成 EXISTENCE——8 条里错 3 条。这是实测出来的，不是推演。

## 7. 校验器规则（关系校验器，10 条）

除 `分工.md` §四.3 的十条外，本次补充一条（同为参与项规则）：

> **同一关系内不能重复引用同一目标**。否则 `I` 的成员数可被"同一命题写两遍"凑到 ≥2。

规则全集以 `RelationValidator` 为准，它对三条链路是**同一个事实来源**：R02/R03 写入校验、GR02 图示校验、关系裁定自定义关系。

## 8. 前端怎么接（给做关系裁定页的人）

1. 用 fixture 起手：`docs/fixtures/relation-adjudication-ses-1.json` 里的 `items` 与真接口同形。
2. 列表按 `items[]` 渲染：左"仅 A 版/B 版"徽章用 `conflictType`，附一行 `reason`。
3. 每项动作：采用V1 / 采用V2（`ADOPT_VERSION` + `sourceVersionId`）、删除（`DELETE`）、自定义（`CUSTOM`）、提交专家（`ESCALATE_EXPERT`）、确认一致（`CONFIRM_AGREEMENT`）。
4. `nestedFirst = true` 的项要提示"先裁内层"。
5. 自定义关系弹窗的选择范围是**统一命题集合**（`us-1`），不是源版本命题；提交时端点填 `us-pN`。
6. `status = COMPLETE` 才允许进入"生成正式版本"；`INCOMPLETE` 提示还有 `pendingItemIds.length` 项；`INVALID` 显示 `issues[]`。
7. 论证图直接复用已有的 `ArgumentGraph.vue`（`graph` 字段形状与 GR01 一致）。
