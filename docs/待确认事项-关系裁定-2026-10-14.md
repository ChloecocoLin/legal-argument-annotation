## 议题 1（影响最大）：J06 的 item 能不能带追加字段

**现状**：契约把 J06 的 item 标了 `additionalProperties: false`，只声明 `{id, conflictType}`。我返回了超集，多了 `dimension / reason / candidates / status / decisionId / nestedFirst` 六个字段。

**为什么**：只给 `{id, conflictType}`，关系裁定页画不出「两侧候选 + 中文差异理由」——裁定者看不到 V1 和 V2 各写了什么、差在哪，就没法在「采用 V1 / 采用 V2 / 自定义 / 退回重标」之间做选择。这六个字段全部是页面渲染的必需项。

**建议**：接受超集。契约未对 J06 之外的追加字段做禁止，前后向兼容；不新增接口、不多一次请求。

**若不同意**：改为前端另调一个「裁定项候选详情」接口取这六个字段。代价是新增一个接口 + 列表页 N 次额外请求（或一个批量接口），且两份数据要保证同源。

**决议**：＿＿＿＿＿＿＿＿＿＿＿＿

## 议题 8：鉴权上线后，**所有人**的接口都要令牌（分工.md §六）

**现状**：C 的公共基础工作里包含「登录、Spring Security、RBAC」。鉴权已**默认全站开启**——`anyRequest().authenticated()`，只白名单三条：登录接口、健康检查（`/actuator/health`、`/actuator/info`）、接口文档（`/v3/api-docs/**`、`/doc.html`、`/swagger-ui/**`、`/webjars/**`、`/favicon.ico`）。

**这对其他人的影响（必须先说清楚，不然会以为是 bug）**：

| 影响 | 说明 |
|---|---|
| **浏览器里所有页面都会跳登录页** | 前端路由守卫按「本地有没有令牌」判定，没登录就跳 `/login?redirect=…`。这是有意的，不是坏了 |
| **裸 curl / Postman 会全部 401** | 先 `POST /api/v1/auth/login`（body `{"username":"…","password":"demo"}`）拿 `data.token`，再带 `Authorization: Bearer <token>` |
| **C 的 8 个自查脚本已改成先登录** | 共用 `scripts/verify_auth.py`。若你们也要写脚本，可以 `from verify_auth import login_token` |
| **角色矩阵只落在 C 的控制器上** | B/D 的接口目前是「登录即可访问」。**B/D 自己的角色矩阵需要你们各自补 `@PreAuthorize`，C 没有代填**——代填等于替别人决定谁能做什么 |

C 已落的矩阵（与 `SecurityConfig` 的 javadoc 一致，`auth-smoke.py` 里是一份可执行版本）：

```
关系实例写（R02–R04）            admin、annotator
论证图写（GR02 审查 / GR03 布局）  admin、annotator、arbiter
关系裁定（J06、裁定结果）         admin、arbiter
教学练习（题库与评分）            admin、student、teacher
读接口（R01、GR01、G07、指南等）   已登录即可
```

**演示账号**（`data.sql` 种子，口令统一 `demo`，登录页上也列了）：`legal.researcher`(admin)、`ann.li`(annotator)、`arb.zhang`(arbiter)、`stu.chen`(student)、`tea.wu`(teacher)。注意 `expert` 角色**没有账号**——它是留给 B/D 的专家复核模块的，C 的矩阵里不含它。

**需要 A/D 确认的三件事**：

1. **要不要把角色矩阵从「C 的模块」推到全站**（B 的指南管理、D 的任务/导出各自该有谁）。这是权限边界，不是代码问题。
2. **接口文档要不要对未登录开放**。目前开放（`/v3/api-docs`、`/doc.html` 免登录）——好处是 A/D 点检和前端联调都方便，代价是**API 全貌对未登录者可见**。真要收紧就把它挂到某个 profile 上，但那会牺牲便利。
3. **口令策略**。种子里是 `{noop}demo`——明文。演示环境可以，**不能带进任何真实环境**。`PasswordEncoder` 用的是带前缀的委托编码器，所以换成 bcrypt 只需改种子里的前缀与值，代码一行不用动；「首次登录强制改密」「口令复杂度」要不要做、谁做，需要定。

**已知取舍（C 自己决定并留档的）**：

- **令牌是不透明串 + 服务端内存会话，不是 JWT**。理由：前端请求封装本来只发 `Authorization: Bearer <token>`，令牌长什么样服务端说了算；而本项目连数据库都是 H2 内存库，签 JWT 只是多一份密钥管理。好处是「登出立刻生效」，JWT 要做到同样的事反而要维护黑名单。
- **没有「免登录开关」**。曾经想加一个 `open` profile 让 A/D 点检时不用登录，但 `@PreAuthorize` 是方法级的：免掉 URL 鉴权也免不掉它，结果会变成「能读不能写」的半开状态，比没有更让人困惑。
- **重启即全体登出**（令牌在进程内存里，与 H2 内存库行为一致）。将来换 MySQL 只需把 `TokenStore` 换成一张令牌表，`issue/resolve/revoke` 三个方法不用变。
- **角色不可自选**。原型 `login.html` 能「选择进入角色」，正式版故意去掉了：角色是账号属性、由后端按令牌判定，前端自选等于把 RBAC 做成摆设。

**决议**：＿＿＿＿＿＿＿＿＿＿＿＿
