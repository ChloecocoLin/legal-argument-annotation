## 议题 1（影响最大）：J06 的 item 能不能带追加字段

**现状**：契约把 J06 的 item 标了 `additionalProperties: false`，只声明 `{id, conflictType}`。我返回了超集，多了 `dimension / reason / candidates / status / decisionId / nestedFirst` 六个字段。

**为什么**：只给 `{id, conflictType}`，关系裁定页画不出「两侧候选 + 中文差异理由」——裁定者看不到 V1 和 V2 各写了什么、差在哪，就没法在「采用 V1 / 采用 V2 / 自定义 / 退回重标」之间做选择。这六个字段全部是页面渲染的必需项。

**建议**：接受超集。契约未对 J06 之外的追加字段做禁止，前后向兼容；不新增接口、不多一次请求。

**若不同意**：改为前端另调一个「裁定项候选详情」接口取这六个字段。代价是新增一个接口 + 列表页 N 次额外请求（或一个批量接口），且两份数据要保证同源。

**决议**：＿＿＿＿＿＿＿＿＿＿＿＿

## 议题 5：SVG / PNG 谁生成、走不走接口（与 D 的边界）

**现状**：`分工.md` §五.5 写「C 提供 SVG、PNG 图文件，D 负责统一导出和历史记录」。但就绪契约 `openapi-ready.yaml` 的论证图接口**只有 GR01 / GR02 / GR03 三个，没有任何导出接口**——SVG/PNG 目前无契约落点。

**建议**：**C 侧纯前端导出，不新增后端接口**。`ArgumentGraph.vue` 的 `serialize()` 已能输出完整 SVG 文档文本，前端 `canvas` 转 PNG 即可，零新依赖（不加 Batik、不动 `pom.xml`）。需要 D 明确的是**导出中心怎么拿到这张图**：
- (a) 浏览器直接下载（C 出文件，D 只导数据）—— 最省，建议；
- (b) D 的导出中心后端渲染 —— 需要新增接口 + 后端图形库，成本最高；
- (c) 导出包里嵌 SVG 文件 —— 折中，D 从浏览器或对象存储取。

**需要 D 拍板的是 (a)/(b)/(c) 选哪个**，这决定 C 下一批是只做前端还是要动后端。

**决议**：＿＿＿＿＿＿＿＿＿＿＿＿
